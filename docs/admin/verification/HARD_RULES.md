| # | Rule | Proof | Test |
|---|---|---|---|
| 1 | Every organisation must have a unique Tenant ID. | `Organization.subdomain` (the canonical Tenant ID referenced by every tenant-scoped document's own `tenantId` field, per this codebase's pre-existing subdomain-based multi-tenancy) carries `unique: true` in the schema (`models/admin/Organization.ts:92`), backed by an application-level pre-check in `createOrganization()` for a friendly error message. | `tests/platform/organizationCreate.test.ts`'s existing "rejects a duplicate subdomain" (the application-level check) plus a **new** test calling `Organization.create()` twice directly, bypassing the application check, proving the database's own unique index is the real backstop for a race between two concurrent creates — not just the friendlier pre-check. |
| 2 | Every tenant-scoped database record must be tenant-isolated. | Pre-existing, codebase-wide convention predating this admin project (`CLAUDE.md` Golden Rules #1/#7: every query includes `tenantId`, every unique index is compound with `tenantId`). This admin project's own contribution is narrower and specific: the one place it necessarily reads across tenants (`lib/platform/tenancy/crossTenant.ts::withCrossTenantRead()`) is the *sole* sanctioned exception, structurally enforced so nothing else can bypass tenant-scoping the way the gateway deliberately does. | `tests/platform/sourceGrep.test.ts` ("crossTenant.ts is never imported from a tenant-facing route" / "...outside app/platform, lib/platform, or app/api/platform") proves the exception stays contained. The underlying "every tenant-scoped model has a compound `tenantId` index" invariant across the full ~pre-existing codebase is not this project's own test to own — it predates the admin build and is out of this brief's scope to re-audit line-by-line. |
| 3 | Global Admin actions must always be auditable. | `withCrossTenantRead()` calls `emitPlatformAuditEvent()` on every invocation, success and denial, before returning (`lib/platform/tenancy/crossTenant.ts:23-26`). Every state-changing admin function (`assignPlan`, `changeOrganizationStatus`, `setOverride`, `setAiLimit`, etc.) does the same at its own call site. | `tests/platform/crossTenant.test.ts`; `tests/platform/sourceGrep.test.ts`'s PlatformAuditLog-mutation-guard describe block (this pass extended it — see rule 14). |
| 4 | AI usage must be metered independently from the UI. | `AiUsageRecord` is written from `lib/ai/tenantAi.ts`'s single real server-side call site — the one place every real AI request passes through regardless of which UI screen initiated it. No UI component writes or can write a usage record itself. | `tests/platform/aiInstrumentation.test.ts`; `docs/admin/verification/ai-metering.md`. |
| 5 | Subscription entitlements must be configuration-driven, not hard-coded. | `resolveEntitlements()` reads `Plan` + `OrganizationEntitlement` documents — no `if (tier === "pro")` conditional exists in the resolution path. `lib/middleware/moduleGate.ts` and `lib/platform/entitlements/enforce.ts` both resolve through it. | `tests/platform/tierEntitlementBridge.test.ts` (17 tests); `tests/internal/orgTier.route.test.ts`. |
| 6 | Plan changes must never silently delete tenant data. | `assignPlan()` (`lib/platform/entitlements/assignPlan.ts`) only ever writes to `Organization` (a `planAssignmentPending` flag), `OrganizationEntitlement` (one upsert), and `SubscriptionEvent` (one append) — by construction, it has no code path touching any tenant business-data collection. | `tests/platform/assignPlan.test.ts`; **new** `tests/platform/sourceGrep.test.ts`'s "Hard Rule 6" describe block — structurally asserts `lib/platform/entitlements/**` and `lib/billing/**` contain no delete-family call (`deleteOne`/`deleteMany`/`remove`/`findOneAndDelete`) at all, so a future edit can't reintroduce one silently, matching rule 7's own PlatformAuditLog guard style. |
| 7 | Audit logs must be append-only/immutable to ordinary application users. | `models/platform/PlatformAuditLog.ts` — Mongoose `pre` middleware rejects `save()` on an existing document and rejects `updateOne`/`findOneAndUpdate`/`updateMany`/`deleteOne`/`findOneAndDelete` outright; `deleteMany` requires an explicit `allowRetentionDelete` query option that only `lib/platform/audit/retention.ts` ever sets (and that deletion is itself preceded by its own audit write). | `tests/platform/sourceGrep.test.ts`'s "PlatformAuditLog is never mutated outside its own model guard" block: no call site anywhere uses a mutating method directly, the model still declares all seven guard hooks, and `allowRetentionDelete` appears nowhere but `retention.ts` and its own test. |
| 8 | Organisation suspension must immediately affect authentication and/or transaction access according to defined policy. | `changeOrganizationStatus()` flips `Organization.isActive`, which `auth.ts`'s `authorize()` reads and rejects sign-in on. **This pass extended the same enforcement to `PAYMENT_HOLD`** (Phase 11 Part 0.3): it was reachable and persisted but had zero behavioural effect until now — a genuinely broken instance of this exact rule, fixed in commit `5191faa`. | `tests/platform/organizationStatus.test.ts` — "suspending an organisation sets isActive=false", "reactivating restores isActive=true", plus this pass's two new cases for PAYMENT_HOLD. |
| 9 | Global Admin access to tenant data must be explicitly permissioned and logged. | `withCrossTenantRead()` requires a capability check (`requireCapability()`) before running, and logs unconditionally — success or denial — via `emitPlatformAuditEvent()`. There is no code path that reads cross-tenant data through this gateway without both. | `tests/platform/crossTenant.test.ts`. |
| 10 | AI cost and usage calculations must be server-side and tamper-resistant. | `AiCostRate` is a server-side rate table; no client request ever supplies a cost figure that gets trusted — every cost calculation derives from `AiUsageRecord`'s server-recorded token counts × the server-held rate. | `docs/admin/OPEN_QUESTIONS.md:29`; `tests/platform/aiDashboard.test.ts`. |
| 11 | Logs must contain structured event types, not only human-readable descriptions. | `PlatformAuditLog.eventType` is a required, enum-constrained field (`PLATFORM_EVENT_TYPE_VALUES`) on every row — never free text. Distinct from the pre-existing tenant `ActivityLog`, which genuinely is free text (documented, not conflated — §18/§19/§20 rows). | Schema-level `enum:` constraint rejects an unrecognised value at the Mongoose validation layer; exercised incidentally by every test that creates a `PlatformAuditLog` row with a real `PLATFORM_EVENT_TYPE` member. |
| 12 | All timestamps should be stored consistently, preferably UTC, with organisation timezone applied at presentation. | **Storage half held already** — every timestamp in this codebase is a Mongoose `Date`, stored as UTC by construction; no code path stores a timezone-local string. **Presentation half was broken and is fixed in this pass.** Checked directly: every timestamp display in the admin control plane (`app/platform/(app)/page.tsx`, `organizations/page.tsx`, `organizations/[id]/page.tsx`, `audit-logs/page.tsx`, `access-requests/page.tsx`) called `.toLocaleString()`/`.toLocaleDateString()` with no timezone argument — which renders in the *viewing admin's browser* timezone, not the organisation's, and never names which zone it used. Fixed via a new shared formatter, `lib/platform/formatting/orgTimezone.ts::formatInOrgTimezone()`, which takes the organisation's own `settings.timezone` (already captured at creation, defaulted from country) and always names the zone in its output; `formatPlatformTimestamp()` is the explicit-UTC sibling for genuinely cross-tenant surfaces (the dashboard, the global audit log, access-requests spanning many organisations) where there is no single "the organisation" whose timezone would apply. Applied to every timestamp display found. The organisation list's two date columns currently use the platform-wide (UTC) formatter as an interim step — Part 1.1's list.ts rework (adding the resolved-plan column) will thread the per-row organisation timezone through so those two columns use `formatInOrgTimezone()` per row, matching the detail page. | `tests/platform/orgTimezone.test.ts` (9 tests) — different organisation timezones produce different displayed times for the same instant, the zone is always named, an invalid/missing timezone falls back to UTC rather than silently using the caller's local zone, and a midnight/date-boundary case (Asia/Kolkata rolling to the next calendar day) is asserted explicitly, matching Phase 11 Part 4's named edge case. |
| 13 | Global Admin and Organisation Admin must have completely separate permission domains. | `AdminUser`/`AdminRole`/`AdminSession` (`models/platform/*.ts`) are a fully separate identity and permission domain from tenant `User`/`master-admin` — zero shared code, zero shared session mechanism, zero shared role table. `lib/platform/auth/adminRbac.ts` resolves capabilities only from `AdminRole`, never touching `User.role`. | `docs/admin/SYSTEM_INVENTORY_DELTA.md` §1; `tests/platform/permissionMatrix.test.ts` (179 tests); `tests/platform/adminRbac.test.ts`. |
| 14 | Sensitive prompts, financial data, credentials, and personal data should not be unnecessarily duplicated into logs. | No model in this codebase's audit/usage surface has a prompt/response/credential field to begin with — `AiUsageRecord` has no prompt/response text field at all (row 17), and `PlatformAuditLog.oldValue`/`newValue`/`metadata` are structured JSON, documented (in `lib/platform/audit/emit.ts`'s own doc comment) as IDs/labels only. That documentation previously described a *convention*, not an enforced guarantee ("this function does not scrub input; callers are responsible") — checked directly, and every real call site today already follows it. **Turned into a structural guarantee in this pass**, matching the enforcement style rule 7 already uses. | **New**: `tests/platform/sourceGrep.test.ts`'s "Hard Rule 14" describe block — extracts every `emitPlatformAuditEvent(...)` and `AiUsageRecord.create(...)` call site's real argument object and asserts no literal key matches a sensitive-field name list (password, secret, token, prompt, response, card/bank/national-ID fields). Includes a synthetic-positive case proving the check would actually catch a real violation, not just pass vacuously. |
| 15 | Every privileged action should have an identifiable actor, timestamp, tenant, session, and outcome. | `PlatformAuditLog` carries `actorId`+`actorRole` (actor), `createdAt` (timestamp, schema-managed), `tenantId`, and `sessionId` on every row. **"Outcome" is encoded via `eventType`, not a separate field** — e.g. `CROSS_TENANT_READ` vs. `CROSS_TENANT_READ_DENIED`, `CAPABILITY_DENIED` — worth stating explicitly since a reader searching for a literal `outcome` field won't find one; the distinct-eventType convention satisfies the same requirement. | `tests/platform/crossTenant.test.ts`; `tests/platform/adminRbac.test.ts`'s `CAPABILITY_DENIED` cases. |

## Summary

- **13 of 15 rules**: solid existing proof, much of it already structurally enforced by a test in
  the style consistent with this project's own precedent (source-grep / model-guard / schema-enum).
- **1 rule genuinely broken, now fixed**: rule 12 (timestamp presentation) — every admin timestamp
  display, fixed this pass, new test suite.
- **3 rules newly given structural enforcement they previously lacked**: rule 14 (sensitive-field
  audit hygiene), rule 6 (no delete call reachable from a plan change), and rule 1 (the database
  unique index on Tenant ID, not just the application-level friendly-error check) — all three held
  in practice, all three now guaranteed by a test rather than by convention or one-off inspection.
- **All 15 rules now have a proof and a test.** No open gaps carried forward from this pass.
