# Kill-Switch Coverage Audit — Phase 10 Addendum A, Part 0

Generated by enumerating every workflow from the live registry (`listWorkflows()`, after
`bootstrapAiRuntime()`) — not a hand-written list — and statically scanning each workflow's real
`index.ts` for `rt.callTool("...")` calls, then resolving each call against the tool registry's
declared `sideEffect` (`read` / `analyse` / `draft` / `execute`). A `draft` or `execute` tool is
"writes anything" for this audit's purposes, including `internal_state`-category writes
(`AiAttentionItem`, `AiCloseAssertion`, `AiControlResult`, `AiEvidencePack`, `AiSchedule`,
`AiLearningRecord`, `AiPaymentHold`, etc.) — not just financial-document writes.

## The defect

`lib/aiRuntime/runtime/eventBus.ts`'s dispatch gate used to exempt a workflow from its own kill
switch whenever its **declared autonomy level** was `OBSERVE` or `RECOMMEND`, on the assumption
those levels never have side effects. That assumption is false. It is false for two different
reasons, both found by this sweep:

1. **9 of 30 workflows declared at `OBSERVE`/`RECOMMEND` write real `internal_state` records** —
   turning their kill switch off did not stop them, because the gate never reached the check.
   These are the "BYPASS" rows below.
2. The old gate's exemption was scoped correctly for the other 10 write-performing workflows
   (`DRAFT`/`EXECUTE`/`CONTROLLED_AUTONOMOUS` autonomy — "gated (above RECOMMEND)" below) — but
   fixing (1) by simply switching the gate to a declared `performsWrites` field and setting that
   field **only on the 9 bypassed workflows** would have silently un-gated all 10 of these
   instead, since the new gate no longer consults autonomy level at all. Caught before commit by
   `tests/ai/aiRuntime/killSwitchCoverage.test.ts`'s third assertion, not by inspection — see
   "How this was caught" below. All 19 real writers now declare `performsWrites: true`.

only requires a kill switch for something that can actually act.

## The fix (structural, not per-workflow)

1. **`lib/aiRuntime/workflows/types.ts`** — added `performsWrites?: boolean` to
   `WorkflowDefinition`: declares whether a workflow's `act()` can reach a write-capable
   (`draft`/`execute`) tool. Optional; a workflow that never sets it is asserted by the coverage
   test (below) to genuinely have no write-capable tool calls.
2. **`lib/aiRuntime/runtime/eventBus.ts`**'s `dispatchEvent()` — the exemption is now
   `if (!enabled && workflow.performsWrites) continue;`, replacing the old
   `defaultAutonomy`-based `requiresValidation`/`exempt` check entirely. A disabled workflow that
   can write is skipped outright (marked processed with zero dispatches, same as before); a
   disabled workflow that cannot write still runs (nothing for the switch to protect).
3. **All 19 real-writer workflows** now declare `performsWrites: true` at their definition site,
   each with an inline comment explaining why (either "this is one of the 9 originally-bypassed
   workflows" or "this was already correctly gated by autonomy level, but the new gate needs the
   field explicitly since it no longer looks at autonomy level at all").
4. **`tests/ai/aiRuntime/killSwitchCoverage.test.ts`** — the structural test, in the style of
   `tests/ai/aiRuntime/safety.test.ts`'s source-grep tests. Reads every registered workflow's real
   source, resolves every `callTool(...)` name against the tool registry, and asserts:
   - every workflow that calls a write-capable tool declares `performsWrites: true` (catches a
     31st workflow reintroducing the original bypass);
   - every workflow declaring `performsWrites: true` actually calls at least one write-capable
     tool (catches the flag being set speculatively / never cleaned up);
   - every workflow that does **not** declare `performsWrites` resolves to zero write-capable
     tool calls (catches the exact regression this fix itself introduced on the first pass — see
     below).

### How this was caught

The first version of this fix set `performsWrites: true` only on the 9 audited BYPASS workflows,
reasoning that those were the only ones the addendum named as suspects. Writing the third
assertion above (read-only-by-omission must mean genuinely no write tools) immediately failed for
AI-01, AI-02, AI-03, AI-05, AI-06, AI-07, AI-08, AI-09, AI-10, and AI-30 — the ones the OLD gate
had already correctly gated by autonomy level, which the new field-only gate would have silently
exempted the moment autonomy level stopped being consulted. This is exactly the class of bug the
addendum's closing note warns about: a fix for one instance of "control that looks enforced but
isn't" introducing a fresh instance of the same shape, caught only because the test asserted the
full registry property (nothing un-declared may write) rather than just the originally-reported
symptom (these 9 named workflows must be covered). Fixed by declaring `performsWrites: true` on
all 19 real writers, not just the 9 named in the addendum's suspect list.

## Part 0.3 — does the same exemption defeat the autonomy clamp?

**Short answer: the same assumption exists in a second place, but it is currently inert — it does
not add any live behavioral exposure beyond what's already fixed above. Recommend leaving it
unless/until something starts relying on it, for the reason below; documenting it here so it's on
record rather than silently re-discovered.**

`lib/aiRuntime/policy/autonomyGate.ts::decideAutonomy()` has its own short-circuit, separate from
`eventBus.ts`'s dispatch gate:

```ts
if (input.requestedAutonomy === AI_AUTONOMY_LEVEL.OBSERVE || input.requestedAutonomy === AI_AUTONOMY_LEVEL.RECOMMEND) {
  return { allowed: true, autonomyApplied: input.requestedAutonomy, escalate: false, ..., clampedBy: "workflow_declared" };
}
```

This runs **before** `policy.maxAutonomyLevel` is ever consulted (the clamp logic is entirely
below this branch). For `OBSERVE`-declared workflows this is correct — `OBSERVE` is the literal
floor of `AI_AUTONOMY_LEVEL_ORDER`, so there is nothing lower to clamp to. But for
`RECOMMEND`-declared workflows (4 of the 9 BYPASS workflows are `recommend`-level: AI-11, AI-12,
AI-19, AI-27 — the other 5, AI-15, AI-18, AI-24, AI-26, AI-29, are `observe`-level, for which the
short-circuit is correct), `OBSERVE` sits below `RECOMMEND` in the order, so
`policy.maxAutonomyLevel = observe` is a
theoretically meaningful, currently-impossible-to-apply clamp — an operator setting it would
expect the workflow to stop acting, and `decideAutonomy()` would never tell them it didn't.

**Why this has no live effect today, checked directly rather than assumed:** `decision` (the
`AutonomyDecision` returned by `decideAutonomy()`) is passed into every workflow's `act()` as its
third parameter. Grepping all 9 BYPASS workflows' `act()` implementations shows **none of them
read `decision.autonomyApplied` or `decision.allowed` to decide whether to call a write tool** —
several (e.g. AI-26) even explicitly `void decision;` to silence the unused-parameter lint. The
only things that currently gate these 9 workflows' writes are (a) the kill switch, now correctly
enforced by the `eventBus.ts` fix above, and (b) for AI-29 and AI-24 specifically, their own
explicit local `isWorkflowEnabled()` checks inside `reason()`/`act()` (defense in depth, predating
this sweep). So today, "fixing" the clamp short-circuit would change what gets recorded on the
decision trace (an honest `escalate: true` when a policy-set ceiling is exceeded) but would change
zero actual write behavior, because nothing downstream consumes the corrected value.

**Recommendation, not applied in this pass:** if `policy.maxAutonomyLevel` is ever meant to be a
real operator lever for `RECOMMEND`-declared writers (as opposed to just the kill switch), two
things would need to happen together — neither of which this brief asked for and both of which
carry real regression risk for zero present benefit:
1. `decideAutonomy()`'s short-circuit would need to apply the clamp for `RECOMMEND` (not just
   `OBSERVE`), which changes `escalate`/`autonomyApplied` recording for all 21 `RECOMMEND`-level
   workflows, not just the 4 writers among them.
2. Every `RECOMMEND`-declared writer's `act()` would need to actually branch on
   `decision.autonomyApplied` before calling its write tool(s) — none currently do.

Left as an open item in `docs/ai/OPEN_QUESTIONS.md` rather than implemented speculatively, per this
project's standing rule to implement the safe/read-only side and record an open question when a
change touches permissions without a concrete, requested need driving it.

## Cross-check against the addendum's named suspects

The addendum named AI-13, AI-24 (close state/assertions), AI-15 (anomaly records), AI-18 (evidence
packs), and AI-27 (holds) as plausible suspects, alongside the confirmed AI-29. Checked against
this sweep:

- **AI-24, AI-15, AI-18, AI-27** — confirmed BYPASS, now fixed. Matches the suspicion exactly.
- **AI-13** — checked and found **not** a bypass: AI-13 (Day-Zero Close) calls no write-capable
  tool at all in the current codebase (it is a pure read/analysis workflow at `OBSERVE`). Named as
  a plausible suspect by the addendum on the reasonable inference that a close-related workflow
  probably writes close state, but the source shows it doesn't (AI-24 is the one that writes
  `AiCloseAssertion`, not AI-13). Reported as a clean answer, not silently dropped.
- Sweep additionally found 4 more BYPASS workflows the addendum did not name:
  **AI-11, AI-12, AI-19, AI-26** — none flagged as suspects in the addendum text, all found only
  by enumerating the full registry rather than checking the named list, which is exactly why
  the addendum insisted on a registry-driven sweep instead of a hand-written one.
