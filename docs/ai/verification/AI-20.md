## 9. Bugs found and fixed

**Real bug found (C.6 adversarial pass) — root cause, fix, and regression test.**

**Root cause.** `matchPair()` in `lib/aiRuntime/relatedParty/detectRelatedParties.ts` treated any
matching, non-empty `gstin` or `pan` string as sufficient evidence for a `certain` government-ID
match, with **no format validation at all**:

```ts
if (cGstin && vGstin && cGstin === vGstin) {
  certain = true;
  matchedOn.push("tax_registration_number");
}
```

Real-world ERP data commonly leaves this field as a placeholder (`"NA"`, `"N/A"`, `"PENDING"`,
`"-"`) when a vendor/customer is unregistered or the field wasn't captured — a well-known Indian
ERP data-quality pattern. Two **genuinely unrelated** companies that both left `gstin` as `"NA"`
would satisfy `cGstin && vGstin && cGstin === vGstin` (both truthy, both equal) and be flagged
`certain: matched on tax_registration_number` — the workflow's *highest* confidence tier, the one
most likely to be accepted at face value by a human reviewer without further checking. This is
precisely the shape Part C.6 asks for: a confidently wrong answer a human would accept, not an
error that gets investigated.

**Fix.** Added the same canonical GSTIN format (`/^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z][0-9A-Z]Z[0-9A-Z]$/`,
matching `lib/migration/validation.ts`'s own `GSTIN_RE`) and a standard PAN format
(`/^[A-Z]{5}[0-9]{4}[A-Z]$/`) as local constants, and gated both `certain`-match branches on the
value actually matching its real format:

```ts
if (cGstin && vGstin && cGstin === vGstin && GSTIN_RE.test(cGstin)) { ... }
if (cPan && vPan && cPan === vPan && PAN_RE.test(cPan)) { ... }
```

This is a **format-validation fix, not a denylist** of known placeholder strings — deliberately, so
it also catches placeholders not enumerated in advance (`"TBD"`, `"XXX"`, `"0000000000"`, etc.)
rather than only the ones anticipated today. A genuinely different, unusually-formed but real
government ID would not be affected differently than before (real GSTINs/PANs already conform to
these fixed statutory formats).

**Regression tests** (`tests/ai/aiRuntime/ai20RelatedPartyDetectionEdgeCases.test.ts`):
1. Two unrelated companies sharing placeholder `gstin: "NA"` → `match` is `undefined` (no longer
   flagged).
2. Same class, PAN side: shared placeholder `pan: "PENDING"` → `classification: null`.
3. **Root-cause proof, not just symptom**: a real, valid-format PAN shared between two
   differently-named companies is still correctly flagged `certain` — proving the fix is format
   validation (still correctly detects real matches), not an overcorrection that broke detection
   entirely.

All three pass. The pre-existing base-suite test (`"a shared tax registration number is a certain
match"`, using a valid-format GSTIN) and the cross-tenant test (also valid-format) were re-run and
still pass unchanged — the fix does not affect any correctly-formatted real identifier.
