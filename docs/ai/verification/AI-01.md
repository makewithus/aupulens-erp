## 5. Failure paths

- **Missing config (unknown vendor / no TaxRate matches within tolerance)**: escalates with a named reason (`"unknown_vendor"` / `"tax_mismatch"`), never guesses. `index.ts:243-268`.
- **Duplicate detected**: escalates CRITICAL, no Invoice created. `index.ts:213-221`; golden case `duplicate-bill-flagged`.
- **Arithmetic invalid**: escalates, no Invoice created. `index.ts:223-231`; golden case `arithmetic-mismatch-escalates`.
- **Non-INR currency (no FX source)**: escalates rather than guessing a conversion. `index.ts:233-241`; golden case `non-inr-escalates`.
- **Kill switch off / permission denied**: `act()` catches the `draft_bill` tool call failure and falls back to propose-only — no partial write, no throw into the business route (`index.ts:317-333`). Covered by `ai01DocumentIngestion.test.ts`'s "no acting user" test and the generic `safety.test.ts`/`autonomyGate.test.ts` suite.
- **Tool failure mid-pipeline (`link_evidence` after `draft_bill` succeeds)**: if `link_evidence` throws, it propagates as an uncaught exception from `act()` — the executor's generic mid-pipeline-failure handling (`executor.ts`, exercised by `safety.test.ts`'s "✓ every AI action is fully audited" test) finalizes a `failed` `AiDecisionTrace` rather than silently swallowing it. The Invoice already drafted by `draft_bill` is NOT rolled back — this is a real, currently-undocumented partial-write risk between two sequential tool calls in `act()` (both individually idempotent, but not atomic as a pair). **Reported as a finding**, not fixed in this pass — see §9.
- **Model unavailable/malformed source data**: not applicable to AI-01's own code (see §4, C.5) — the upstream OCR failure path (`extractDocument`'s `gated`/error branches) is `lib/docIntel/extractor.ts`'s own contract, tested by the trigger-proof route test's use of the real (mocked-at-the-boundary) route, and is out of this workflow's scope.

## 9. Bugs found and fixed

1. **Cross-tenant data leak via unscoped `findById`** — `index.ts` (`extract()`, was line 94) used `ExtractedDocument.findById(observed.raw.extractedDocumentId)` with no `tenantId` filter. A hostile or malformed `document.received` event referencing another tenant's `ExtractedDocument` id would be read cross-tenant (violating CLAUDE.md's own Golden Rule #1), and at DRAFT autonomy could draft an Invoice under the wrong tenant using another tenant's confidential bill data. **Root-cause fix**: scoped the query to `{ _id, tenantId: ctx.tenantId }`. **Regression test**: `ai01DocumentIngestionEdgeCases.test.ts`, "C.4 cross-tenant hostile input." **Class, not incident**: the identical unscoped-`findById` shape was found and fixed in AI-02 (`Invoice`/`Expense` lookups) and AI-03 (`BankStatement` lookup) in this same pass — **flagged to the requester for a check across the other 27 workflows**, since `extract()` reading its own subject record by a raw event-supplied id is the exact same shape used throughout the workflow catalogue.
2. **Unescaped user input interpolated into a MongoDB `$regex`** — `index.ts` (`extract()`, vendor lookup) built `{ $regex: `^${extraction.vendorName.trim()}$` }` directly from OCR-extracted vendor text. A name containing regex metacharacters (`.`, `(`, `+`, etc. — all legal in real business names) could either silently false-match an unrelated vendor (`.` matches any character) or throw "Invalid regular expression" on an unbalanced group, crashing the run instead of escalating cleanly. **Root-cause fix**: added `escapeRegex()` and applied it before interpolation. **Regression tests**: two cases in `ai01DocumentIngestionEdgeCases.test.ts` (metacharacter false-match, unbalanced-paren crash). **Class, not incident**: the same unescaped-`$regex` pattern exists in `lib/aiRuntime/workflows/ai-10-fixed-asset/index.ts:198` and the shared `lib/aiRuntime/tools/financeReadTools.ts:52` (`nameContains` filter, used by multiple workflows) — **flagged, not fixed** (out of this chunk's scope; AI-10 and the shared tool file are not AI-01's own files).
3. **Ambiguous vendor match silently resolved to an arbitrary record** — `Vendor.name` has no uniqueness constraint, not even compound with `tenantId` (`models/admin/Vendor.ts`), so two real Vendor records can legally share a name. The old `Vendor.findOne(...)` picked whichever record MongoDB returned first, with no ambiguity detection — the exact "a vendor whose name matches two real vendors" adversarial case the brief names explicitly (Part C.6). **Root-cause fix**: changed to `Vendor.find(...)`; 2+ matches now escalate as `"ambiguous_vendor"` instead of picking one. **Regression test**: `ai01DocumentIngestionEdgeCases.test.ts`, "C.6 adversarial." **Confirmed not a class beyond this workflow** — no other workflow in this batch performs a vendor-name-to-single-record match the same way (AI-02/AI-03 match by amount/date/rule, not by name-uniqueness assumption).
4. **Reported, not fixed (out of scope)**: `lib/docIntel/billCreate.ts::loadExistingBills` caps at `.limit(2000)` with no sort, risking missed duplicates for a >2000-bill tenant (see §4 "Large"); and `act()`'s sequential `draft_bill` → `link_evidence` tool calls are not atomic as a pair (see §5) — both are real findings surfaced by this pass but live outside `lib/aiRuntime/workflows/ai-01-document-ingestion/`, so left unfixed per this chunk's scope constraints.
