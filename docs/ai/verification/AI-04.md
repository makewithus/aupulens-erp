## 9. Bugs found and fixed

**Bug 1 — cross-tenant data leak in `extract()` (FIXED).**
`lib/aiRuntime/workflows/ai-04-expense-intelligence/index.ts`'s `extract()` used to call
`Expense.findById(observed.raw.expenseId)` with **no `tenantId` filter**. A hostile or spoofed
event whose declared `tenantId` doesn't match the referenced Expense's real tenant — reachable via
`lib/aiRuntime/nl/chatBridge.ts::runWorkflowFromChat()`, which calls `runWorkflow()` directly and
is not gated by any `subscriptionFilter` — could read another tenant's private expense data and
evaluate it against the attacking tenant's own `AiExpensePolicy`, leaking the amount/category into
that tenant's `AiAttentionItem` queue. Proved directly: constructed a tenant-B Expense (₹999,999)
and a tenant-A policy with a ₹100 travel limit, then ran AI-04 with a tenant-A event referencing
the tenant-B expense id — before the fix, this produced an "over_limit" finding quoting 999999
under tenant A.
**Root-cause fix**: scoped the query to `Expense.findOne({ _id: observed.raw.expenseId, tenantId:
ctx.tenantId })`, so a cross-tenant reference now fails closed as "not found" (same code path as a
genuinely-missing record — see §5).
**Regression test**: `tests/ai/aiRuntime/ai04ExpenseIntelligenceEdgeCases.test.ts` — "cross-tenant
hostile input."
**Same class checked elsewhere**: yes — found and fixed identically in **AI-07** (two locations:
`accuracy_check`'s `Invoice.findById`, `reversal_run`'s `AiSchedule.findById`) and **AI-08** (two
locations: `detect`'s `Invoice.findById`, `execute`'s `AiSchedule.findById`) — see those records'
§9. **Not checked/fixed in the other 27 workflows** — flagged to the task owner as a defect class
worth a systematic `findById`-without-tenant-filter audit across `lib/aiRuntime/workflows/**`,
since the same "fetch subject by id in `extract()`" pattern is used everywhere and the same
`chatBridge.ts` bypass applies to every workflow with a `subscriptionFilter`-gated eventKey.

**Finding 2 — event-bus silently skips dispatch for a never-validated tenant (REPORTED, NOT
FIXED — out of scope).** `lib/aiRuntime/runtime/eventBus.ts::dispatchEvent` skips a workflow
entirely (no `AiWorkflowRun`, no trace, no visible reason anywhere) when `isWorkflowEnabled()` is
false (kill switch off/unconfigured) **and** the workflow's `defaultAutonomy` is above `RECOMMEND`
— true for AI-04 (`DRAFT`). This means C.4's "nothing configured → degrades to RECOMMEND, states
which setting is missing" holds for a **direct** `runWorkflow()` invocation but not for the real
event-driven path on a genuinely never-configured tenant, where it is instead total silence.
Verified directly (see the probe described in §1). This is shared runtime code
(`lib/aiRuntime/runtime/eventBus.ts`), not AI-04's own file, and out of this task's scope to fix —
reported to the task owner as a systemic issue affecting all 30 workflows whose `defaultAutonomy`
exceeds `RECOMMEND`, not unique to AI-04.

**Finding 3 — concurrent duplicate-event race (REPORTED, NOT FIXED — out of scope).**
`runWorkflow()`'s idempotency check (`lib/aiRuntime/runtime/executor.ts:52-54`, find-then-create on
`{workflowId, triggerEventId}`) is not atomic. Firing the same trigger event twice via
`Promise.all` (simultaneous, not sequential) results in the second concurrent call throwing an
unhandled `MongoServerError: E11000 duplicate key error` instead of gracefully returning the first
call's envelope. Data integrity is **not** compromised — exactly one `AiWorkflowRun` row persists
either way — but the caller-facing behaviour on a genuine race is a crash, silently swallowed by
`safeEmitEvent()`'s catch-all in production rather than surfaced. Shared executor code, out of
scope for this task; reported to the task owner as affecting all 30 workflows identically.
