## 1. Trigger proof

AI-06 has two real event keys: `bill.created` (per-bill PO matching + duplicate detection) and
`ai.sweep.hourly` (due schedule + payment-run proposal).

**`bill.created`** is emitted from exactly one real call site today:
`lib/docIntel/billCreate.ts::createDraftBill()` (the document-intelligence "confirm extracted
vendor bill" step), line ~105, via `safeEmitEvent()`. New test:
`tests/ai/aiRuntime/ai06PayablesOperationsEdgeCases.test.ts` › `"trigger proof: the real
createDraftBill() service (not runWorkflow()) fires AI-06's bill_match and detects a PO
mismatch"` — calls the real exported `createDraftBill()` with a PO reference and an over-quantity
line, and asserts an `AiWorkflowRun` for AI-06 was created with `matchResult.verdict === "exception"`.
`runWorkflow()` is never called directly in that test. **Passed.**

**Real, honest finding**: `app/api/finance/bills/route.ts` — the ordinary manual "create a vendor
bill" form/route that a Finance user uses day-to-day — does **not** emit `bill.created` anywhere
(confirmed by grep across `app/**`/`lib/**` for `safeEmitEvent`/`bill.created`; the only hit is
`billCreate.ts`). AI-06's own code is correct and fires exactly on what it subscribes to; the gap
is a missing emit in a *different* file, out of this pass's scope (only AI-06's own source under
`ai-06-payables-operations/` is in scope to fix). **Consequence**: today, a manually entered
vendor bill never gets AI-06's PO-matching/duplicate-detection intelligence at all — only a bill
confirmed through document intelligence does. The `ai.sweep.hourly` mode (due schedule/payment
run) still covers every open bill regardless of how it was created, since it queries `Invoice`
directly rather than reacting to the creation event. Flagged here for whoever owns
`app/api/finance/bills/route.ts` next.

**`ai.sweep.hourly`** is emitted by `app/api/cron/ai/runtime-sweep/route.ts`, proven for AI-06 by
the large-volume test in section 4 (real `runWorkflow()` sweep, not the cron route directly — the
cron-route path itself is proven generically for this event key by AI-09/AI-30's own trigger-proof
tests against the same route).

### Cross-tenant defect-shape check (the prior finding named in this pass's brief, AND the
### AI-06 `partnerId` claim specifically requested for verification)

**The prior batch's spot-check claim — "`Customer.findById(invoice.partnerId)`/`Customer.
findById(bill.partnerId)` are safe because they resolve a field on an already tenant-scoped
parent document" — was independently re-verified and found to be materially incomplete, though
not exploitable via the event payload directly.**

Confirmed true: `invoice` (bill-match mode, `Invoice.findOne({_id, tenantId, moveType})`) and
`bill` (sweep mode, `Invoice.find({tenantId, moveType, ...})`) are both genuinely fetched
tenant-scoped — an attacker cannot supply a cross-tenant `invoiceId` in the `bill.created` payload
and have AI-06 read a different tenant's `Invoice`.

**But the claim's reasoning does not hold**: `invoice.partnerId`/`bill.partnerId` are fields ON
that tenant-scoped document, and nothing guarantees they reference a Customer in the SAME tenant.
Traced the write path: `app/api/finance/bills/route.ts` (the manual bill-creation route), line
~138, does `let partnerId = body.partnerId;` and uses it directly at bill creation with **no check
that the referenced Customer belongs to the caller's tenant**. A bad or hostile write through that
route can therefore leave a real, tenant-scoped `Invoice` whose `partnerId` points at another
tenant's real `Customer` document. The subsequent unscoped `Customer.findById(invoice.partnerId)`
in AI-06's `extract()` would then read — and expose, in this workflow's own findings/attention
items/due-schedule output — that other tenant's vendor name. This is the same defect *class* named
in the brief (an unscoped fetch of an externally-influenceable id), reached through a different
injection point (an upstream write-path gap) rather than directly through AI-06's own event
payload.

**Root-cause fix** (both occurrences, `lib/aiRuntime/workflows/ai-06-payables-operations/
index.ts`): changed `Customer.findById(invoice.partnerId)` and `Customer.findById(bill.partnerId)`
to `Customer.findOne({ _id: ..., tenantId })`, scoping both reads to the current tenant regardless
of what the upstream write path allows. **Regression tests**:
`ai06PayablesOperationsEdgeCases.test.ts` › `"cross-tenant hostile: a bill whose partnerId points
at another tenant's Customer never leaks that vendor's name"` (bill-match mode) and `"...the
sweep's due-schedule vendor-name cache never resolves another tenant's Customer either"` (sweep
mode) — both assert the victim tenant's real vendor name never appears anywhere in AI-06's output,
falling back to `""`/`"Vendor"` instead. Existing 12-case unit suite re-run clean after the fix.

**The upstream gap itself** (`app/api/finance/bills/route.ts` accepting `body.partnerId` with no
tenant-ownership check) is a real bug but is in a different file, out of this pass's scope to fix
(only AI-06's own source is in scope). Flagged here for whoever owns that route next — the same
shape plausibly exists on other manual-entry routes that accept a `partnerId`/`customerId`
directly from the request body; not checked across the other 29 workflows' write paths in this
pass.

### Adversarial pass: vendor-mismatched PO — real defect found and fixed

**The question asked**: what input makes AI-06 produce a confidently wrong "match" a human would
approve for payment? Answer: a bill from vendor B whose `poReference` happens to name a PO that
actually belongs to vendor A, with line quantities/prices that agree with that PO. Traced both
AI-06's own PO lookup and the pre-existing real matcher it explicitly defers to
(`lib/accounting/matching.ts::runPOMatching()`, confirmed by reading it) — **neither ever checked
that the referenced PO belongs to the same vendor as the bill**. `PurchaseOrder` names are unique
only per `{tenantId, name}` (confirmed in the schema, `PurchaseOrderSchema.index({tenantId:1,
name:1}, {unique:true})`), not per vendor — so this is a real, reachable case (a data-entry
mistake or a fraudulent bill copying a real PO number), not a contrived one. Previously, such a
bill came back `verdict: "match"` — a textbook confidently-wrong answer.

**Root-cause fix** (`lib/aiRuntime/workflows/ai-06-payables-operations/index.ts`, `extract()`):
after fetching the PO, compare `String(po.partnerId) !== String(invoice.partnerId)`; if they
differ, force `verdict: "exception"` regardless of line-level agreement and prepend a variance
string naming the vendor mismatch explicitly. Vendor identity always wins over line-level
agreement. **Regression test**: `ai06PayablesOperationsEdgeCases.test.ts` › `"adversarial: a bill
referencing a DIFFERENT vendor's real PO, with agreeing line amounts, is an exception — never a
confident match"`. **Same class checked**: the identical gap exists in
`lib/accounting/matching.ts::runPOMatching()` itself (the real, pre-existing three-way matcher
used elsewhere in the system) — confirmed by reading it, **not fixed** (out of this pass's scope:
that file is shared runtime/accounting code, not AI-06's own source). Flagged explicitly as the
same defect class, present in the system's non-AI matching path too, not just AI-06's own
independent computation.

## 9. Bugs found and fixed

1. **Cross-tenant vendor-name leak via an unscoped `Customer.findById()`** — both call sites in
   `lib/aiRuntime/workflows/ai-06-payables-operations/index.ts` (bill-match mode and sweep mode).
   Root cause and fix: see the dedicated analysis above. The prior verification pass's
   spot-check claim that these were "safe because they resolve a field on an already tenant-scoped
   parent document" is corrected here: the parent document being tenant-scoped does not make its
   *foreign-key field* trustworthy — the actual guarantee needed (and now enforced) is scoping the
   dependent read itself. **Same class checked**: confirmed absent in AI-30 and AI-05 (both
   verified directly in this same pass — see their own records' cross-tenant sections); the
   upstream write-path gap that makes this reachable (`app/api/finance/bills/route.ts` accepting
   an unvalidated `body.partnerId`) was not checked across the other 29 workflows' own write paths
   in this pass — flagged as worth a targeted audit.

2. **Vendor-mismatched PO producing a confident "match"** — `lib/aiRuntime/workflows/
   ai-06-payables-operations/index.ts`'s own PO lookup, AND the pre-existing
   `lib/accounting/matching.ts::runPOMatching()`. Root cause and fix (AI-06's own file only, per
   scope): see the dedicated adversarial-pass analysis above. **Same class named, not fixed,
   elsewhere**: `runPOMatching()` itself has the identical gap and is out of this pass's file
   scope — flagged explicitly for a future pass, not silently left.

3. **Standard-write permission requires a real, persisted `User`** — not a bug, documented
   explicitly (same finding as AI-05's, section 9 there) because it was initially mistaken for one
   while writing the concurrent-duplicate test.

4. **Timezone/period-boundary gap** — named as a defect class shared with AI-30/AI-05 (see
   AI-30.md section 9, item 3). Not fixed here (systemic, out of this file's scope).
