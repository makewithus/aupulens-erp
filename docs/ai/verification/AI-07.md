## 5. Failure paths

- **Locked period**: caught, period left pending for the next sweep, no partial write (§4, C.3/C.5).
- **Kill switch off**: clamps to RECOMMEND, findings still surfaced, no journal written (§4, C.4).
- **Permission denied**: clamps to RECOMMEND via the shared gate.
- **Tool failure mid-pipeline**: caught generically in `act()`'s try/catch, no partial write, retried on the next sweep.
- **Model unavailable**: not applicable — no model calls.
- **Malformed source data**: covered, no crash, amounts rounded to the cent (§4, C.1).
- **Missing/cross-tenant subject record**: `extract()` throws, executor marks the run `failed` with a finalized trace — same mechanism as AI-04 (§9).

## 9. Bugs found and fixed

**Bug 1 — cross-tenant data leak in `extract()`, two locations (FIXED).** Same defect class as
AI-04's Bug 1: `accuracy_check`'s `Invoice.findById(observed.raw.invoiceId)` and `reversal_run`'s
`AiSchedule.findById(observed.raw.scheduleId)` both had no `tenantId` filter. The `reversal_run`
case is the more serious of the two: `subscriptionFilter`'s `scheduleBelongsTo()` ownership check
only runs on the `eventBus.ts` fan-out path — `lib/aiRuntime/nl/chatBridge.ts::
runWorkflowFromChat()` calls `runWorkflow()` directly and bypasses it entirely, so a hostile
`scheduleId` parameter reaching AI-07 through chat could have read (and, before the fix, could
have posted a reversal journal against) another tenant's `AiSchedule`/`PurchaseOrder` data.
**Root-cause fix**: both queries now scope to `{_id, tenantId: ctx.tenantId}`; a cross-tenant
reference fails closed as "not found." **Regression tests**: two tests in
`ai07AccrualIntelligenceEdgeCases.test.ts` — one per branch — both assert the run throws/escalates
and no journal is posted under the attacking tenant, and that the victim tenant's schedule is left
untouched. **Same class checked elsewhere**: found and fixed identically in AI-04 (one location)
and AI-08 (two locations, same shape) — see those records' §9. Reported as a defect class for the
other 27 workflows (not fixed here, out of scope) — see AI-04's record §9 for the full note.

**Bug 2 — month-length boundary bug in the GRNI accrual's reversal date (FIXED).**
`act()`'s `draftable` loop computed the reversal date with
`reversalDate.setUTCMonth(reversalDate.getUTCMonth() + 1)` on a fresh `new Date()`. JS's own Date
mutation semantics roll this over into the month *after* the intended one whenever the current
day-of-month exceeds the target month's length — e.g. drafted on Jan 31, the reversal date became
**March 3**, not February 28, silently scheduling the reversing entry a full extra month late.
Proved directly: `node -e` reproduction (`new Date(Date.UTC(2026,0,31))` + `setUTCMonth(+1)` →
`2026-03-03T00:00:00.000Z`) before the fix, and confirmed the same bug reaches the real
`AiSchedule.periods[0].periodKey` via `lib/aiRuntime/tools/scheduleWriteTools.ts`'s
`draftAccrualHandler`, which derives the period key directly from `reversalDate`.
**Root-cause fix**: added `addOneMonthClamped(date)` — adds one calendar month and clamps the
day-of-month to the target month's real last day (standard "add one month" semantics) — and
replaced the mutating `setUTCMonth` call with it.
**Regression test**: `ai07AccrualIntelligenceEdgeCases.test.ts` — "month-length boundary: an
accrual drafted on Jan 31 reverses in February, not March" — uses `vi.setSystemTime` to pin "today"
to Jan 31 2026 and asserts the resulting schedule's `periodKey` is `"2026-02"` (not `"2026-03"`)
and `dueDate` is clamped to Feb 28.
**Same class checked elsewhere**: grepped `lib/aiRuntime/workflows/ai-08-prepaid-schedule/
index.ts` and `ai-04-expense-intelligence/index.ts` for `setUTCMonth`/`setMonth`/`setDate`/
`setFullYear` — none found; AI-08's own period-end math uses `Date.UTC(...)` direct construction
(not mutation), which is not subject to this specific pitfall (verified empirically with several
month-length cases, including Dec 31 fiscal-year-end wrap and a Jan 29 leap-year case — all
produced correct results). **This is a real defect shape worth a targeted grep across the other 27
workflows** (`setUTCMonth\(.*\+.*1\)|setMonth\(.*\+.*1\)` on a mutated `Date` object, as opposed to
`Date.UTC(...)` direct construction) — flagged to the task owner, not checked exhaustively here.
