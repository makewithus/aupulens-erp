## 5. Failure paths

- **Missing config**: covered — degrades to explicit `policy_gaps` findings naming exactly what's
  missing, never a vacuous "consistent" (section 4, C.4).
- **Locked period**: N/A — AI-26 never touches a locked accounting period.
- **Kill switch off**: dispatches at OBSERVE per Hard Rule 6 (the lowest autonomy level — OBSERVE
  never writes a business record regardless), no partial state.
- **Permission denied**: both tools are `internal_state`, structurally exempt by design.
- **Tool failure mid-pipeline**: proven via the generic executor mechanism (section C.3/C.5) — a
  thrown write escalates to a `FAILED` trace, never a partial `AiPolicyFinding`.
- **Malformed source data**: proven not to crash in section 4 (missing-accountId/unicode test).

Every path escalates or no-actions cleanly; none silently swallow into a false "consistent" result.

## 6. Output contract

Envelope: `lib/aiRuntime/contracts/outputContract.ts::WorkflowRunEnvelope`, generic conformance
proven by `tests/ai/aiRuntime/executor.test.ts`. AI-26's own proposal shape (`Ai26Proposal`):
`policies[]`, `treatmentVerdicts[]`, `inconsistencies[]`, `policyGaps[]`, `impactOfChange[]` — every
field always a populated array (never `undefined`). One field is **not** honestly populated: `
policies[].coverageCount` is hardcoded to `0` for every existing policy regardless of actual
coverage — never computed, and not represented as an explicit "not computed" null either. No test
anywhere asserts on this field and nothing downstream reads it, so it carries no functional risk
today, but it does not meet section 6's "every field populated or explicitly null with a reason"
standard. **Not fixed in this pass** (computing a real, honest coverage count per policy key is
non-trivial new logic beyond this verification chunk's bug-fixing mandate) — flagged here rather
than silently left undocumented; recommend either computing it for real or removing the field
until it can be.

## 9. Bugs found and fixed

1. **Cross-tenant hostile input — checked specifically per this chunk's mandate, no defect found
   (no injection point exists at all).** `observe()` returns `{ entityId: event.tenantId, raw: {
   triggered: true } }` — `ai.sweep.hourly`'s payload is `{}`, carrying no record id, model name,
   or any externally-supplied value whatsoever for AI-26 to trust. Every one of `extract()`'s five
   queries (`collectInheritedPolicyGaps`, `findCapitalizationInconsistencies`,
   `findUncoveredTransactionTypes`, `AiAccountingPolicy.find`, `AiMaterialityPolicy.findOne`) is
   called with only the trusted `ctx.tenantId`, confirmed by direct code reading and by a full grep
   of every `findById`/`findOne(` call across `lib/aiRuntime/policyIntelligence/*.ts` (all four
   matches are `{tenantId}`-scoped). **New test added anyway** (section 4, C.4) to prove this in
   behaviour: a tenant with a real inconsistency and threshold never leaks into a second tenant's
   own run. AI-26 does **not** have the AI-01/02/03/04/07/08/09/10 defect shape — unlike AI-19
   (which resolves an event-supplied `{model, recordId}` pair) and AI-27 (which reuses AI-19's
   detector), AI-26's single trigger carries no externally-supplied identifier to resolve at all,
   so there is structurally no injection point to exploit, not merely one that happens to be
   scoped correctly.

No code bugs were found in AI-26 itself requiring a root-cause fix in this pass. Two honest
limitations were found and are documented rather than silently passed over: the always-hardcoded
`coverageCount: 0` field (section 6) and the always-present, potentially stale-reading inherited-gap
headline (section 4, C.6) — both are pre-existing, deliberate-or-low-risk shapes rather than the
kind of exploitable defect this chunk's bug-hunting mandate targets, and neither has a test
depending on the current (arguably wrong) behavior, so fixing either would not be blocked by
regression risk in a follow-up pass.
