## 5. Failure paths

- **Missing config (no threshold)**: `RECOMMEND`, `threshold_configured=false` stated explicitly
  in the finding detail, never an invented number — `ai10FixedAsset.test.ts`.
- **Locked period**: `try/catch` in `act()`, period stays pending — module comments, generic
  `check_period_lock` mechanism.
- **Kill switch off**: never dispatched — event-bus gate.
- **Permission denied**: `gateOverrides.permissionOk` false → capped at `RECOMMEND`; `act()`'s own
  `decision.autonomyApplied === RECOMMEND` guard returns immediately for `schedule_init` and
  `depreciation_run`.
- **Tool failure mid-pipeline**: per-call `try/catch`; generic mid-pipeline-failure trace test.
- **Malformed source data**: proven not to crash (section 4); asset-live checks (`assetActive`)
  prevent posting against a disposed asset.

None silently swallow into a false-clean result; none partially write (each write is a single,
idempotency-keyed tool call; the two-step `draft_journal` + `link_schedule_draft` pair only links
after the journal draft has genuinely succeeded and returned a real ID).

## 9. Bugs found and fixed

Three related cross-tenant defense-in-depth gaps, all in
`lib/aiRuntime/workflows/ai-10-fixed-asset/index.ts`, all fixed in this pass:

1. **`schedule_init` branch** (was: `Asset.findById(observed.raw.assetId).lean()`) — a foreign
   tenant's real `assetId` would have been read and could have started a depreciation schedule
   against it under the wrong tenant. **Fix**: scoped to
   `Asset.findOne({ _id: observed.raw.assetId, tenantId: ctx.tenantId })`; a cross-tenant ID now
   fails closed with the existing `"Asset ... not found"` error (run marked `failed`, no data
   read or written). **Regression test**: `"cross-tenant hostile: asset.created carrying another
   tenant's real assetId is refused..."`.
2. **`depreciation_run` branch's `owned` check** (was: `scheduleType === DEPRECIATION &&
   sourceRef.model === "Asset"`, no tenant check) — identical shape to the bug found and fixed in
   AI-09's own `schedule_run` branch (see AI-09's verification record, section 9). **Fix**: added
   `schedule.tenantId === ctx.tenantId` to the `owned` boolean. **Regression test**:
   `"cross-tenant hostile: schedule.due carrying another tenant's real scheduleId is refused..."`.
3. **`capital_check` branch** (was: `Invoice.findById(observed.raw.invoiceId).lean()`) — a foreign
   tenant's real bill would have been read and its data (vendor, line items, amount) exposed in
   this tenant's own finding/attention item. **Fix**: scoped to
   `Invoice.findOne({ _id: observed.raw.invoiceId, tenantId: ctx.tenantId })`. **Regression
   test**: `"cross-tenant hostile: bill.created carrying another tenant's real invoiceId is
   refused..."`.

All three regression tests pass; the full existing `ai10FixedAsset.test.ts` and golden-dataset
suites re-run clean after the fix (9/9 and 4/4 respectively).

**Same class checked across other workflows**: this is the same defect shape found in AI-09
(section 9 there) — confirmed also present, unfixed, in **AI-07** and **AI-08**'s own
`schedule.due` handling (both out of this pass's scope; reported to the orchestrator, not fixed
here). Worth a systematic audit: any `extract()` that does `Model.findById(<payload-supplied
id>)` without a `tenantId` filter is this same class, and AI-10 alone had three instances of it in
one file — it is plausible other workflows accepting a record ID via their trigger payload
(`bill.created`, `invoice.created`, `expense.submitted`, etc.) have the same gap.
