## Cross-tenant hostile-input check (specifically requested)

**Checked every DB read in `extract()`: no unscoped-cross-tenant-fetch defect exists in AI-16.** `BankAccount.find({tenantId})`, `BankStatement.findOne({tenantId, ...})`, `FxRate.findOne({tenantId, ...})`, `AiSchedule.find({tenantId, ...})`, `Payroll.find({tenantId, ...})`, and the two sibling-trace reads `AiDecisionTrace.findOne({tenantId, workflowId: "AI-05"})` / `"AI-06"` (`index.ts:199,220`) — **all scoped to `ctx.tenantId`**, never to an externally-supplied id. `computeBankPosition(tenantId, String(statement._id))` (AI-03's own function, reused rather than reimplemented) is called with a statement id that AI-16 itself just looked up via a tenant-scoped query, not one supplied by the event payload. AI-16's event payload carries only an optional `actingUserId` (never used in a DB read). No externally-supplied record id exists for this workflow to resolve at all. Confirmed by new test: tenant A's forecast, run with tenant B's own user id passed as the (unused-for-lookups) `actingUserId`, correctly totals only tenant A's ₹5,000 balance (never tenant B's ₹10,000,000) and correctly names the missing AI-06 schedule as tenant A's own omission rather than silently inheriting tenant B's ₹999,999 due-bill trace.

## Adversarial pass (Part C.6) — detailed

**Question asked**: what input makes AI-16 produce a confidently-wrong forecast a human would accept? **Answer considered and tested**: a predicted inflow landing exactly on the horizon's boundary day. A careless `<=` vs `<` off-by-one in the day-bucketing loop could either silently drop a real, large receivable from the forecast entirely (understating available cash and creating a phantom shortfall) or double-count it across two adjacent days (overstating cash and hiding a real shortfall) — either is a "confidently wrong, easily accepted" forecast, since a shortfall/no-shortfall headline number is exactly what a reviewer skims. New test confirms the boundary is handled correctly: a ₹40,000 receivable dated exactly `today + 29 days` (the last valid index in the `0..29` horizon) appears exactly once, on the final forecast day, verified via the exact closing-balance arithmetic (`1000 opening + 40000 inflow = 41000`, not ~1000 or ~81000). No bug found here — documented as a real risk that was specifically checked, not assumed safe.
