# AI-05 — Verification Record

Workflow: `lib/aiRuntime/workflows/ai-05-receivables-operations/index.ts` (Receivables operations)

## 1. Trigger proof

AI-05 has no dedicated per-record business action (receivables ops is a continuous sweep, not a
create-a-record hook) — its real trigger is `ai.sweep.hourly`, emitted exclusively by
`app/api/cron/ai/runtime-sweep/route.ts` (the real Vercel Cron endpoint) via `emitEvent()` →
`eventBus.dispatchEvent()` → `runWorkflow()`.

New test: `tests/ai/aiRuntime/ai05ReceivablesOperationsEdgeCases.test.ts` ›
`"trigger proof: the real cron sweep route (not runWorkflow()) fires AI-05 and drafts a
collection-worklist communication"` — seeds a real `Organization` + an overdue `SalesInvoice`,
calls the real exported `POST` handler from the cron route file, and asserts an `AiWorkflowRun`
for AI-05 was created and a real `AiCommunicationDraft` was written. `runWorkflow()` is never
called directly in that test. **Passed.**

**Important nuance found while writing this test** (not a bug — see section 9 for why): the real
cron route always emits `ai.sweep.hourly` with an **empty payload** (`emitEvent(subdomain,
"ai.sweep.hourly", {})`, no `actingUserId`). AI-05's core financial write,
`draft_receipt_allocation`, is gated on `gateOverrides.permissionOk = Boolean(extracted.
actingUserId)`, which is therefore always `false` on the real unattended trigger. In production,
the fully unattended hourly sweep reports allocation candidates, opens disputes, and drafts
collection communications — but it **never itself writes the receipt allocation**; that action
only fires when a human explicitly invokes AI-05 with an identified acting user (e.g. AI-NL's
`handleWorkflowIntent()`, which injects `actingUserId: userId` —
`lib/aiRuntime/nl/workflowChatHandler.ts:46`). A dedicated new test proves this explicitly:
`"the real unattended sweep (no actingUserId) reports the allocation candidate but never writes
draft_receipt_allocation"`.

### Cross-tenant defect-shape check (the prior finding named in this pass's brief)

**AI-05 has no injection point of the "unscoped `Model.findById()` on an event-payload-supplied
id" shape.** Confirmed by reading the whole file: `observe()` reads only `event.payload.
actingUserId` (a string, used solely for `gateOverrides.permissionOk` and passed through on the
output — never as a lookup key). Every query in `extract()` — `SalesInvoice.find`, `Payment.find`,
`Invoice.find`, `AiMaterialityPolicy.findOne` — filters directly on `tenantId: ctx.tenantId`, with
no id read from the event payload at all. There is no record-id parameter anywhere in this
workflow's data path for a hostile payload to bind to. Asserted directly (new test, above).

## 5. Failure paths

- **Missing config**: proven, section 4 — degrades to informational reporting, reason stated.
- **Locked period**: `try/catch` at every write call site, generic mechanism proven in
  `toolRegistry.test.ts`.

independently idempotency-keyed).

## 6. Output contract

Envelope: generic `WorkflowRunEnvelope`. AI-05's own proposal shape (`Ai05Proposal`):
`allocationCandidates[]`, `predictedPayments[]`, `worklist[]`, `agingSummary`,
`paymentStateDivergence`, `unallocatedCash` — every array field is always populated (empty, never
`undefined`) when there's nothing to report; `agingSummary` is the pass-through GL-derived report
object. Findings carry `subjectRefs` for disputes (`SalesInvoice`) and empty `subjectRefs` for
unallocated-cash findings (no single subject to point at — a payment/customer pairing, not a
record with an open-balance problem of its own), with the payment itself always cited in
`evidence`.

## 9. Bugs found and fixed

1. **Cross-tenant defect shape** — checked directly, **not present**. See the dedicated analysis
   in section 4/C.4 above. No fix needed.

2. **The real unattended trigger never supplies an acting user, so `draft_receipt_allocation`
   never fires from it** — investigated as a potential bug, confirmed **not a bug**: every
   existing allocation-asserting test in `ai05ReceivablesOperations.test.ts` already passes an
   explicit `actingUserId`, which is the correct, intentional shape — a real financial write
   (`models/sales/Payment.ts`, not an `internal_state`/`Ai*` model) goes through the standard
   `routePermissionCheck`, which requires a real acting principal even at `DRAFT` tier, by design
   (the same pattern `draft_match_annotation` uses in AI-06 — see AI-06.md). What this pass adds
   is making that behaviour **explicit and tested** rather than implicit in which tests happened
   to pass a user id: the new "no actingUserId" test in section 1 pins down exactly what the
   fully unattended hourly sweep does and does not do. Recorded here because it materially
   qualifies the Trigger Proof claim ("fires unprompted") — see the VERDICT below.

3. **Timezone/period-boundary gap** — named as a defect class shared with AI-30/AI-06 (see
   AI-30.md section 9, item 3). AI-05's own date math (`differenceInCalendarDays`, `addDays`) is
   safe from the specific leap-day/month-mutation bug shape found in AI-09, but consults no
   tenant-timezone concept at all. Not fixed here (systemic, out of this file's scope).
