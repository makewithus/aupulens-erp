## Cross-tenant hostile-input check (known defect class 1)

**Checked every DB read reachable from AI-18's own code: no unscoped-cross-tenant `findById` on an event-payload-supplied id exists.** `observe()` takes only `event.payload.period`/`periodEnd` (strings) plus the generic, attribution-only `actingUserId` — never used in a lookup. `extract()`/`act()` resolve accounts exclusively through `annotateStatement()` (tenant-scoped throughout its own report/coverage/reconciliation/close-state reads) and the real `build_evidence_pack`/`traceAccountEvidence` calls (tenant-scoped). Confirmed by new test with real, differing, deliberately large (₹999,999) data seeded on tenant B and a hostile `actingUserId` belonging to tenant B: tenant A's findings and evidence pack never reference tenant B's account, and no `AiEvidencePack` was ever written for tenant B (proving no cross-write either, since AI-18 was never run for it).

## Adversarial pass (Part C.6) — detailed

**Question asked**: what input would make AI-18 confidently report "fully evidenced" when real material gaps remain unaddressed? **Answer found — a real bug, not a hypothetical**: a tenant with more than `MAX_ACCOUNTS_PER_SWEEP` (20) unsupported-material accounts in one period. The sweep cap only *builds* an evidence pack for the first 20; before this pass's fix (documented directly in `index.ts`'s own comment, but never covered by a test until now), `completenessScore` was computed as `1 - missingEvidenceCount / checkedCount` — scored only over the 20 accounts actually checked. If those 20 happened to evidence cleanly, the score reported `1.0` ("fully complete") while the remaining accounts — known material and unsupported — were silently never evidenced that run at all. **This is exactly the "confidently wrong answer a human would accept" shape Part C.6 asks for**: a reviewer trusting `completenessScore: 1` would have no reason to look further. Root-caused and fixed (§9), with a new regression test proving the fix.

## 9. Bugs found and fixed

1. **`MAX_ACCOUNTS_PER_SWEEP`'s completeness score silently reported "fully evidenced" while real material gaps went unchecked — source fix pre-dated this pass, but had never been tested until now.** Investigated per the task's explicit instruction to check what `MAX_ACCOUNTS_PER_SWEEP` is for and whether it's tested — it was not. Read `index.ts`'s own comment (lines 165-177) documenting the original defect precisely: with more than 20 swept accounts, `completenessScore` used to be `1 - missingEvidenceCount / checkedCount` (checkedCount capped at 20) — the denominator excluded the very items the cap skipped, so a tenant with 25 unsupported-material accounts where the first 20 evidenced cleanly reported `completenessScore: 1` while 5 known-bad accounts were never evidenced that run. **Verified the fix directly against the real `act()`** (not trusted from the diff): new test "bug regression: with more swept accounts than MAX_ACCOUNTS_PER_SWEEP (20), completenessScore counts every unchecked account as incomplete and states how many were skipped" constructs 25 real `Account` documents, calls the real `act()` (with the real `build_evidence_pack`/`record_evidence_pack` tools via the real tool registry — only the account-*selection* step, `annotateStatement()`, is bypassed, since standing up 20+ genuinely material-and-unreconciled *distinct* accounts through the real reconciliation engine isn't naturally possible — there are only ~10 reconciliation definitions total, `lib/aiRuntime/reconciliation/definitions.ts`), and asserts: exactly 20 accounts get a real evidence pack built (the cap), `completenessScore` is computed against the full 25 (`Math.max(0, 1 - (missingEvidenceCount + uncheckedCount) / sweptTotal)`, matching `index.ts` exactly) and is therefore `< 1`, never a false "fully complete," and a real `ANOMALY` finding states "25 account(s) ... only the first 20 ... 5" by name — never silent. A companion **false-positive test** ("exactly MAX_ACCOUNTS_PER_SWEEP (20) swept accounts — nothing is skipped") confirms no phantom "not yet evidenced" finding fires when the population sits exactly at the cap, not over it. Both pass. **Class check**: `MAX_ACCOUNTS_PER_SWEEP`-style caps (a bounded per-run population with a "did we check everything" scoring risk) were checked for AI-29 in this same pass — AI-29 has no equivalent cap (`create_task`'s own per-control exception cap was removed entirely in this pass as a *different* bug, §9 of `AI-29.md`) — and AI-17 has no bounded-population cap of any kind (its obligation/registration-gap population is config-sized, never transaction-volume-capped). Not checked across the other 27 workflows (out of this task's scope); **flagged as a class worth a targeted check**: any workflow that caps a per-run population (`slice(0, N)` or similar) and then scores "completeness"/"coverage" only over the capped subset is at risk of this exact shape.
