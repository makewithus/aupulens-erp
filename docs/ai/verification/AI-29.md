## Cross-tenant hostile-input check (known defect class 1)

**Checked every DB read reachable from AI-29's own code: no unscoped-cross-tenant `findById` on an event-payload-supplied id exists.** `observe()` takes only `event.payload.period` (a string) — there is no externally-supplied *record id* anywhere in AI-29's input for the AI-01..04/07-10 defect shape to attach to, structurally the same as AI-14/AI-17/AI-18 (period/sweep-triggered workflows with no subject id in their payload). Every `population()` query in `definitions.ts` is scoped to `tenantId` explicitly.

**One unscoped `findById` does exist**, noted for completeness rather than fixed as this defect class: `bank_detail_change_process.test()` (`definitions.ts:359`) calls `AiHold.findById(item.holdRef)` with no `tenantId` filter. This is **not exploitable** the way the known class is: `holdRef` is never taken from an event payload or user input — it comes from `AiMasterDataProfile.bankChangeAlerts[].holdRef`, itself read from a query already scoped to `{tenantId, ...}` one line earlier in the same `population()`. A cross-tenant leak would require a different tenant's `AiHold._id` to already be recorded inside this tenant's own `AiMasterDataProfile` document — a data-integrity problem elsewhere, not a lookup this control could itself cause. Flagged, not fixed (out of this task's file scope, and not the named defect shape).

## 9. Bugs found and fixed

1. **Duplicate `AiAttentionItem` per exception, from two independently-built `dedupeKey` formats.** `act()` (`lib/aiRuntime/workflows/ai-29-control-monitoring/index.ts`, pre-fix lines ~173-189) called `create_task` explicitly for every `critical`/`high` exception with `dedupeKey: \`ai29-exception-${controlId}-${ref}\`` (no prefix). But every exception is *also* already pushed as an `EXCEPTION`-type finding in `reason()`, and the executor's own generic per-finding escalation (`lib/aiRuntime/runtime/executor.ts`, "an EXCEPTION-type finding ... always gets an attention item") *already* calls `createAttentionItem()` for every one of them, using `dedupeKey: \`${workflow.id}:${finding.id}\`` = `AI-29:ai29-exception-${controlId}-${ref}`. Two call sites, two different-looking keys for the same logical exception → two upserted rows instead of one. **Root cause**: AI-29's own `act()` duplicated work the shared executor already does universally for every workflow. Confirmed by comparison with AI-22 — the identical "one engine, many definitions" reconciliation workflow — which never had a second call site; it relies on the generic mechanism alone. **Fix**: removed the redundant explicit per-exception `create_task` loop (and the now-unused `MAX_EXCEPTION_TASKS_PER_CONTROL` constant) from `act()`, keeping the design-concern `create_task` call (an `ANOMALY`-type finding, which the generic per-finding escalation does *not* cover unless the whole run escalates — no duplication risk there). **Regression test**: `ai29ControlMonitoringEdgeCases.test.ts` › "concurrent duplicate period.horizon.reached dispatch..." now asserts exactly 1 `AiAttentionItem`, and passes. **Class check**: AI-17 and AI-18 (this same task's scope) were read and confirmed to make **zero** explicit `create_task`-style calls for regular exceptions — they rely on the generic mechanism alone, so they do not share this shape. Not checked across the other 27 workflows (out of this task's scope) — **flagged as a class worth a targeted grep** (`create_task.*dedupeKey.*exception` or similar) across every workflow that both pushes `EXCEPTION` findings *and* calls `create_task` explicitly in `act()`.

2. **Test bug (not a product bug): `approval_present.populationSize` was asserted to be 10,000 under a threshold set specifically so "none of these trip approval_present."** `approval_present.population()` (`lib/aiRuntime/controls/definitions.ts`) — like `journal_documentation` and `approver_authority` — deliberately filters its population to only the items actually subject to the control (`amountTotal >= threshold`) *before* returning; `populationSize` (`controls/engine.ts`) is `population.length`, i.e. post-filter. With the fixture's own threshold (₹1,000,000) exceeding every seeded entry's ₹100, the *correct* `populationSize` is 0, not 10,000 — the inherited test's own stated intent ("none of these trip approval_present") directly contradicts its assertion of a non-empty population. **Fix**: corrected the test's expectation to `populationSize: 0, exceptions: []` for `approval_present`, and added an assertion against `no_posting_into_locked_period` (whose population has no threshold filter) to genuinely exercise the 10,000-item scale path the test was meant to prove. **Regression test**: the corrected test itself, now passing and measuring real elapsed time (§8).

3. **Test bug (not a product bug): kill-switch-off was asserted to suppress all AI-29 writes.** Investigated against `lib/aiRuntime/policy/autonomyGate.ts` and `lib/aiRuntime/runtime/eventBus.ts` per the task's own instruction, rather than assumed either way. Two independent, already-tested places in the shared runtime agree the kill switch has nothing to gate for an OBSERVE-ceiling workflow: `decideAutonomy()`'s OBSERVE/RECOMMEND short-circuit runs *before* `kill_switch_enabled` is ever evaluated (own comment: "OBSERVE and RECOMMEND never write anything real... so they need no gating at all" — already asserted green in `autonomyGate.test.ts`'s "OBSERVE and RECOMMEND require no gate at all — allowed even with terrible inputs", which passes `killSwitchEnabled: false` and expects `allowed: true`); and `dispatchEvent()`'s own `requiresValidation` check only skips a disabled workflow *above* RECOMMEND. AI-29's writes (`record_control_result`, `create_task`) are both `category: "internal_state"` — internal monitoring/reporting records, not business documents, exactly the class the write-permission gate exists to let through regardless. Suppressing them would also directly contradict Part 9's own false-completion rule (silently losing all compliance-monitoring visibility with no stated reason when an unvalidated kill switch is off, rather than continuing to observe and report). **Conclusion: the test's expectation was wrong, not the product.** **Fix**: rewrote the test to assert the actual, deliberately-designed, doubly-confirmed behaviour (control results and a real SoD-conflict attention item are still written), with the full reasoning documented inline. **Class check**: this reasoning is generic to every OBSERVE/RECOMMEND-ceiling workflow (not AI-29-specific) and is already covered structurally by `autonomyGate.test.ts`'s existing, generic test — no further per-workflow check needed for this specific shape.
