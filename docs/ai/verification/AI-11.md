## 5. Failure paths

- **Missing config (no inventory account)**: `resolveInventoryAccountMapping` returns
  `resolved: false` with a stated reason; the reconciliation leg still runs (against whatever
  accounts the mapping *did* resolve, or reports the mapping gap as part of the proposal) — never
  an invented account.
- **Kill switch off**: not applicable to AI-11 (RECOMMEND-only, always runs, never writes a
  business record) — see C.4 above.
- **Permission denied**: not applicable — no permission-gated write.
- **Tool failure mid-pipeline**: propagates to a `failed` run (no `try/catch` swallowing it),
  proven generically by `safety.test.ts`.
- **Malformed source data**: proven not to crash (section 4).

Nothing silently swallows into a false "reconciled" result — the subledger-to-GL leg's
`unreconciled` status is itself surfaced as a HIGH-severity finding, never suppressed.

## 6. Output contract

Envelope: `WorkflowRunEnvelope` (generic). AI-11's own proposal shape (`Ai11Proposal`): `period`,
`inventoryAccountMapping`, `subledgerToGl` (`null` until `act()` computes it, then always fully

`valuationAnomalies[]`, `slowMoving[]`, `marginAlerts[]` — every array field defaults to `[]`, not
`undefined`, so a consumer never has to distinguish "not computed" from "computed, found nothing."

## 9. Bugs found and fixed

No bug was found in `lib/aiRuntime/workflows/ai-11-inventory-cogs/` itself in this pass — its own
`extract()`/`reason()`/`act()` are correct, tenant-scoped, and idempotent by construction.

**Fixed in a later pass (Chunk 10, P0.3, docs/ai/BRIEF-10-PRE-QA.md)**: `lib/aiRuntime/inventory/
detect.ts` — physically outside the `ai-11-inventory-cogs/` folder, though it is AI-11's own
exclusive detection logic (the workflow's own module doc comment calls it out as "the real
logic"). Two real N+1 performance concerns, both now fixed:

1. `detectCountVariances` used to run a `Stock.aggregate()`, a full `computeWeightedAverageCost()`
   call, and a `Product.findOne()` — three round trips — per counted product. Fixed: the small set
   of most-recently-counted products is resolved first, then system quantities/WAC/names are each
   fetched with exactly one bulk query/computation for the whole set.
2. `computeMarginByProduct` was the worst of the four: for **every product**, it called
   `marginForPeriod()` twice (current + prior month), and each call re-ran a full-period
   `Invoice.find()` with no product filter at all — re-scanning the ENTIRE period's invoice set
   once per product, not just one query per product. Fixed: one bulk `Invoice.aggregate()` per
   period (current, prior), grouped by product server-side — 2 round trips total regardless of
   product count. **Measured**: 2,000 products against 4,000 real invoices now resolves in
   **~50ms** (`tests/ai/aiRuntime/ai11WorkflowEdgeCases.test.ts`'s new dedicated stress test,
   which the prior 1,500-product test never actually exercised — it seeded zero invoices, so this
   exact worst-case path was never stressed until now).

`detectNegativeStock` was re-read and confirmed to already query in bulk (one `Stock.find({tenantId})`
for every product, processed in memory — no per-product loop). `detectSlowMoving`, on the other
hand, turned out to have the SAME shape as the other two — a per-distinct-product `Stock.findOne()`
plus `Product.findOne()`, missed by this record's first pass at fixing this class. **Also fixed
now**: one `Stock.aggregate()` gets every product's own latest movement timestamp in a single
pass; one bulk `Product.find()` resolves names only for the products that turn out stale.
**Regression test**: `ai11InventoryCogs.test.ts` › "detectSlowMoving: a product with no movement
in 180+ days is flagged; one with recent movement is not." All four of AI-11's detectors are now
confirmed bulk, not per-product-looped, and `computeMarginByProduct` — the worst offender — is
measured at ~50ms for 2,000 products against 4,000 real invoices (`ai11WorkflowEdgeCases.test.ts`'s
new dedicated stress test), closing the coverage gap this record originally flagged (the old
1,500-product test never seeded any invoices, so this exact path was never actually stressed).
