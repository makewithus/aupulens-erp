## 5. Failure paths

  `resolved: false` with a stated reason; the reconciliation leg still runs (against whatever
  accounts the mapping *did* resolve, or reports the mapping gap as part of the proposal) — never
  an invented account.
- **Kill switch off**: not applicable to AI-11 (RECOMMEND-only, always runs, never writes a
  business record) — see C.4 above.
- **Permission denied**: not applicable — no permission-gated write.
- **Tool failure mid-pipeline**: propagates to a `failed` run (no `try/catch` swallowing it),

- **Malformed source data**: proven not to crash (section 4).

Nothing silently swallows into a false "reconciled" result — the subledger-to-GL leg's
`unreconciled` status is itself surfaced as a HIGH-severity finding, never suppressed.

## 9. Bugs found and fixed

No bug was found and fixed **inside this pass's scope** (`lib/aiRuntime/workflows/ai-11-inventory-cogs/`
itself has no bug — its own `extract()`/`reason()`/`act()` are correct, tenant-scoped, and
idempotent by construction).

**Reported, not fixed (outside scope)**: `lib/aiRuntime/inventory/detect.ts` — physically outside
the `ai-11-inventory-cogs/` folder, though it is AI-11's own exclusive detection logic (the
workflow's own module doc comment calls it out as "the real logic"). Two real performance
concerns, both N+1 query patterns, worth a dedicated pass:

1. `detectNegativeStock`, `detectValuationAnomalies` (via `computeWeightedAverageCost`),
   `detectCountVariances`, and `detectSlowMoving` all loop over every product/count individually
   with their own per-iteration query — O(products) round trips instead of a batched read.
2. `computeMarginByProduct` is the worst of the four: for **every product**, it calls
   `marginForPeriod()` twice (current + prior month), and each call re-runs
   `Invoice.find({tenantId, moveType:"out_invoice", invoiceDate:{...}})` — fetching the **entire**
   period's invoice set again, unfiltered by product, then filtering client-side. This is
   O(products × invoices-in-period) work, not O(products) — at a real tenant's scale (thousands
   of products, thousands of monthly invoices) this is the one most likely to blow the 10s budget
   or force AI-11 into an async/background shape it doesn't currently have.

This was measured, not just theorized: the 1,500-product test in this pass (1.07s) did **not**
exercise `computeMarginByProduct`'s expensive path because no invoices were seeded for it — so
that number is not evidence the margin computation scales safely. **This is a genuine gap in this
verification pass's own coverage**, named honestly rather than glossed over: a true 10k+
product/invoice large-volume test for the margin path specifically was not built, because fixing
what it would likely reveal is outside this pass's file-scope. Recommend a follow-up pass that
either (a) batches these four detectors in `lib/aiRuntime/inventory/detect.ts`, or (b) makes
AI-11 explicitly async with a visible pending state per Part E.3's rule for anything that can't be
brought under 10s.
