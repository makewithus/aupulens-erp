## 1. Trigger proof

AI-30 has no per-record business action — it is an hourly health sweep (`ai.sweep.hourly`),
emitted exclusively by `app/api/cron/ai/runtime-sweep/route.ts` (the real Vercel Cron endpoint,
bearer-secret gated) via `emitEvent()` → `eventBus.dispatchEvent()` → `runWorkflow()`. For a
sweep-shaped workflow this cron route *is* the ordinary business action.

New test: `tests/ai/aiRuntime/ai30ErpOperationsEdgeCases.test.ts` ›
`"trigger proof: the real cron sweep route (not runWorkflow()) fires AI-30 and it detects a
dead-lettered event"` — seeds a real `Organization` + a dead-lettered `AiEvent`, calls the real
exported `POST` handler from the cron route file (no mocking of the AI runtime), and asserts an
`AiWorkflowRun` for AI-30 was created, its decision trace's proposal contains the
`dead_lettered_event` issue, and the real repair (`requeue_dead_lettered_event`) actually ran —
the event's status flips `dead_letter` → `pending`. `runWorkflow()` is never called directly in
that test. **Passed.**

## 2. Golden dataset result

### Cross-tenant defect-shape check (the prior finding named in this pass's brief)

**AI-30 has no injection point of the "unscoped `Model.findById()` on an event-payload-supplied
id" shape found across AI-01/02/03/04/07/08/09/10.** Confirmed by reading the whole file:
`observe()` returns `{ entityId: event.tenantId, raw: { triggered: true } }` — it never reads
anything from `event.payload` at all. `extract()` begins with `void observed;` and never touches
`observed.raw` again; every one of the 11 detectors in `lib/aiRuntime/opsHealth/detect.ts` is
called with `ctx.tenantId` as its only argument and every underlying Mongoose query filters on
`tenantId` directly. There is no record-id parameter anywhere in this workflow's data path for a
hostile payload to bind to. Asserted directly (new test, above): a payload naming another
tenant's real `AiEvent` id is completely inert.

## 8. Performance

Measured, not invented:

- Real cron-route trigger, single tenant, one dead-lettered event: included in the ~1.3–1.5s
  fan-out cost shared with every other sweep-triggered workflow in the same cron request (same
  shared cost documented in AI-09's own record).
- Direct `runWorkflow()` sweep, 10,000 dead-lettered events (grouped across 25 event keys,

  a systemic-outage scenario, not the expected steady state.
- Healthy-tenant / small-broken-tenant sweep (existing unit suite): consistently under 600ms.

## 9. Bugs found and fixed

1. **Unguarded per-issue repair call and findings-record call in `act()`** —
   `lib/aiRuntime/workflows/ai-30-erp-operations/index.ts`. Every repair handler behind
   `rt.callTool()` already resolves its OWN internal failures to `{repaired:false, reason}` rather
   than throwing, but `callTool()` itself (or anything upstream of the handler — a repair-gate
   read failing, a permission/autonomy-exceeded error) can still throw. Unguarded, one bad repair
   among several independent ones aborted the **entire sweep**: every remaining repair in the
   `for` loop, and the `record_operations_findings` call that persists that hour's whole health
   report, both silently never ran — a healthy list of correctly-detected issues could be lost
   for an entire hour because of one unrelated failure. **Root-cause fix**: wrapped each per-issue
   repair call in its own `try/catch` (recording `outcome: "failed — <message>"` on exception) and
   wrapped the trailing `record_operations_findings` call in `try/catch` (best-effort, matching
   AI-05/AI-06's own record-keeping call pattern). **Regression test**:
   `ai30ErpOperationsEdgeCases.test.ts` › `"one repair throwing (repair-gate outage) does not
   block the other repair or the sweep's own findings record"` — mocks `checkRepairGate` to throw
   for one specific issue key only (`vi.mock` over the real module, `vi.importActual` for
   everything else); asserts the other, independent repair still succeeds and
   `AiOperationsFinding` is still written. **Same class checked**: this is a variant of the
   general "one item's tool-call exception aborts an otherwise-independent batch" shape — AI-05
   and AI-06's own `act()` loops already isolate every per-item tool call in `try/catch` (checked
   directly by reading both files during this pass), so this shape was contained to AI-30's own
   two unguarded call sites, not present elsewhere in these three workflows. Not re-checked across
   the other 27 workflows (out of this pass's scope) — worth a targeted grep for "a `for`/`.map`
   loop over independent items with an un-try/catch'd `rt.callTool()` inside it" in a future pass.

2. **Cross-tenant defect shape (the prior finding named in this pass's brief)** — checked
   directly, **not present**. See the dedicated analysis in section 4/C.4 above: `extract()` never
   reads `observed.raw`, and every detector is called with `ctx.tenantId` only. No fix needed.

3. **Timezone/period-boundary audit (Part C.2)** — named as a **defect class**, not fixed here:
   `findStaleTaxProjections()`'s period-boundary math (`periodStart`/`periodEnd` built from UTC
   month boundaries) does not consult `Organization.settings.timezone`, which exists in the schema
   but is read nowhere in this workflow (or, on inspection, anywhere in AI-05/AI-06's own date
   logic either — see their own verification records). This is a systemic gap across every
   date-comparing AI workflow, not unique to AI-30, and fixing it correctly would require a
   coordinated change to a shared date-utility layer well beyond this pass's file scope (only
   `ai-30-erp-operations/`'s own source). Flagged explicitly rather than silently left blank.
