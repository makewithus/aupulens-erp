# AI-22 — Verification Record

Workflow: `lib/aiRuntime/workflows/ai-22-continuous-reconciliation/index.ts` (`eventKeys: ["period.horizon.reached", "ai.sweep.hourly"]`, `actionClass: "read_only"`, `defaultAutonomy: OBSERVE`). A thin OBSERVE-level wrapper over `lib/aiRuntime/reconciliation/engine.ts`, which runs all 12 registered reconciliation definitions (`lib/aiRuntime/reconciliation/definitions.ts`) and turns the results into findings. Never writes, never invokes another workflow.

Passed (1.3s).

## 2. Golden dataset result (Chunk 10, P0.6 — closes the "no golden dataset" limit)

AI-22 now has a real golden dataset: `tests/golden/ai22/goldenCases.ts` + `tests/golden/ai22.golden.test.ts`, **24/24 cases (100%)**, following the same `tests/golden/ai27/` shape every other dataset in this project uses. One correct-answer case + one must-stay-silent case for every definition with a real `run()` (`bank`, `ap_control`, `ar_control_finance`, `fixed_assets`, `inventory`, `payroll`, `suspense_clearing`, `tax`, plus `prepaid`/`deferred_revenue` — two more real, registered definitions the original brief didn't name but that would otherwise have zero golden coverage), the two permanently `not_implemented` siblings (`intercompany`, `processor_settlement`), and two dedicated P0.5 cases (below) proving the new closed-period scoping. 100% threshold: AI-22 has zero model calls anywhere in its path, fully deterministic. Building this dataset itself caught and fixed one real bug — a sign error in one of the definitions producing a magnitude-correct-but-sign-flipped difference, confirmed by the golden test failing hard with exactly that symptom before the fix.

Two additional golden-harness regression tests lock in the P0.5 decision below: the SAME open AP/AR balance still computes a real number for the tenant's current open period (only a genuinely closed one is scoped out), and AI-13's `closeReadiness` domain reports `NOT_CHECKED` — never a fabricated `ready` or `blocked` — when it consumes a closed-period `ap_control`/`ar_control_finance` result.

`tests/ai/aiRuntime/ai22ContinuousReconciliation.test.ts`'s 9 pre-existing cases remain as additional coverage, all re-run clean: the `bank` definition produces the exact same numbers as AI-03's own `computeBankPosition()` on the same fixture (never a second implementation); `intercompany`/`processor_settlement` always appear as `not_implemented` with a live reason, never silently dropped; all 12 definitions are always present in the output; `suspense_clearing` reports `not_applicable` (not a false "reconciled") when no account matches; an explicit `AiAccountMapping` overrides the suspense/clearing name-regex heuristic; an unreconciled bank definition raises a real exception finding through the actual workflow run; the `tax` definition reports `not_applicable` with no `TaxRate.accountId` configured, and detects a real, exact 1-unit-scale (₹100) difference once one is.

**P0.5 decision — `ap_control`/`ar_control_finance`'s point-in-time gap (docs/ai/BRIEF-10-PRE-QA.md P0.5):** these two definitions used to compare the AP/AR subledger's CURRENT balance against the CURRENT control-account balance — correct only for the tenant's current, still-open period, since `Invoice` carries no `amountResidual`/payment-application history to reconstruct a past `periodEnd`'s balance. A real point-in-time reconstruction would need that history, which this codebase's schema doesn't carry — too large a lift for this pass. **Decision: explicit scoping, not silent drift.** Both definitions now check the tenant's own `PeriodClosing` record for the requested period (`isClosedPeriod()` in `definitions.ts`) and return a new `"not_supported_for_closed_periods"` status instead of computing anything once that period has been taken past `PERIOD_CLOSING_STATUS.OPEN` — registered as two capability-registry gaps (`ap_control_point_in_time`, `ar_control_finance_point_in_time`, `lib/aiRuntime/capabilities/registry.ts`), so the scoping is visible, not silent. Deliberately keyed to the tenant's own real close action, not a calendar-vs-wall-clock heuristic (an earlier version of this fix compared `periodEnd`'s calendar month against `new Date()`, which silently broke every pre-existing test using a fixed historical period fixture as real time advanced — caught and corrected during this same pass, before merge). `engine.ts` special-cases this status the same way it already special-cases `not_applicable` (never routed through `classifyReconciliationStatus()`, so it can never accidentally read back as a confident `"reconciled"`), and AI-13's `closeReadiness` domain checks (`lib/aiRuntime/closeReadiness/domains.ts`) map it to `NOT_CHECKED`, never a fabricated `ready`/`blocked`.

### Cross-tenant hostile-input check (specifically requested)

**Checked; no defect found.** AI-22's event payload carries only `period`/`periodEnd` (strings) — no subject-record id at all. Every one of the 12 reconciliation definitions in `definitions.ts` takes `tenantId` as its own function parameter and threads it into every query directly (`BankStatement.find({tenantId})`, `Invoice.find({tenantId, ...})`, `JournalEntry.aggregate([{$match: {tenantId, ...}}])`, `TaxRate`/`AiTaxTransaction` queries, etc.) — none accept a record id sourced from AI-22's own payload. One shared helper it calls, `computeBankPosition()` (`lib/aiRuntime/workflows/ai-03-bank-reconciliation/position.ts`, reused verbatim from AI-03), does an internal unscoped `BankStatement.findById(bankStatementId)` — **but AI-22's `bank` definition only ever calls it with an id it just obtained from its own `BankStatement.find({tenantId})` query, never from a payload**, so this is a latent defense-in-depth gap in a shared file (already reviewed once for AI-03's own, different, genuinely exploitable vector — see `docs/ai/verification/AI-03.md` §9, where AI-03's own `extract()` was fixed to scope the id before ever reaching this same helper) and is **not independently exploitable through AI-22**. Flagged for whoever next touches `position.ts`, not fixed here (shared file, out of this pass's scope). New test **"C.4 cross-tenant"** confirms this concretely: tenant A's run, given a hostile `tenantId: OTHER_TENANT` embedded directly in the payload (which `observe()` never reads), reports only tenant A's own ₹100 bank balance, never tenant B's ₹9,000,000. Passed.

## 5. Failure paths

- **Missing/malformed `periodEnd`**: degrades to the current period-end — pre-existing fix, **validated with a real regression test in this session** (§9).
- **Missing `period` label**: degrades to the current month's label; confirmed no literal `"undefined"` ever reaches a persisted finding id (new test).
- **No control account configured, open items exist**: a real, named `configuration_missing` exception, never `not_applicable` (§4 C.4, existing coverage).
- **Sibling capability not implemented** (`intercompany`, `processor_settlement`): reported with a live, registry-sourced reason, never silently omitted (§4 C.5).
- **Kill switch off**: does not gate this workflow at all (OBSERVE-only, by design — §4 C.4).
- **Model/tool unavailable**: not applicable — no model or tool call exists in this workflow.
- **Concurrent duplicate events**: one run persists; the loser may throw (documented executor-level gap, §4 C.3, not fixed here).
