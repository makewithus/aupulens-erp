## Adversarial pass (Part C.6) — detailed

**Question asked**: what input makes `amount_outlier` produce a confidently-wrong-*looking* result a human would accept without checking? (AI-15 never *acts* on a finding, so "confidently wrong" here means "an alarming-looking investigation item for something actually mundane," not a posted error.)

**Answer**: a vendor/account pair with near-zero natural variance (e.g. fixed contractual rent, always the same to the rupee) makes even a small, entirely legitimate change (a contractual rent increase) produce an enormous z-score. New test constructs exactly this: six months of rent at 50000±1, then a legitimate 10% increase to 55000 — the detector fires (confirmed by the test), and does so at whatever severity the z-score computes to (a huge deviation from a near-zero stddev necessarily crosses the `z >= 6` "high" threshold). **This is a real, honest structural property of any z-score-based detector, not something this pass invents a statistical fix for**: AI-15's own architecture already has the correct mitigation built in — every anomaly ships `silent: true` by construction until a detector clears a real review sample at acceptable precision (A.5's precision machinery), and the auto-disable mechanism (already tested generically in `ai15AnomalyDetection.test.ts`'s "a detector below the precision floor...auto-disables") is exactly what corrects a detector that keeps firing confidently-alarming-but-mundane results for a specific low-variance population: repeated reviewer dismissal drives that detector's precision below the 50% floor and it stops raising. This is the intended, designed answer to the adversarial shape, confirmed by direct test rather than assumed.

Guarded degenerate case, confirmed by reading: a population with *literally* zero variance (`stddev === 0`, e.g. identical-to-the-paisa repeats) is explicitly excluded from scoring at all (`stat.stddev > 0.01` guard, `index.ts:299`) — this is the *correct* choice (a zero-stddev population cannot produce a meaningful z-score; scoring it would be a division-by-near-zero producing an infinite, meaningless number), but it also means a truly flat-history vendor gets **no** amount-based anomaly detection at all, at any deviation size. This is a real, honest limitation — not fixed in this pass (changing the statistical approach for degenerate populations is a design decision beyond a verification pass's scope) — flagged here for visibility.

## 9. Bugs found and fixed

1. **Idempotency-defeating `Date.now()` in the write-tool idempotency key — duplicate `AiAnomaly` rows on every re-scan of the same in-window instance.** `index.ts`'s `act()` (was line 552) built `idempotencyKey: \`ai-15-anomaly:${a.detectorId}:${a.subjectRefs[0]?.id ?? a.suppressionKey}:${Date.now()}\`` — the persistent idempotency store (`lib/aiRuntime/tools/registry.ts`'s `callWithPersistentIdempotency()`, backed by `AiToolCall`'s real unique index on `{tenantId, toolName, idempotencyKey}`) can only dedupe two calls whose keys are *identical*; appending `Date.now()` guarantees every call gets a unique key, defeating the mechanism entirely. **Real-world impact, not theoretical**: AI-15's 24h lookback window overlaps ~23 hours between consecutive hourly sweeps, so the *same* detected instance (e.g. one specific outlier `JournalEntry`) is re-evaluated by `reason()` on every sweep it remains inside the window — before this fix, that meant a brand-new `AiAnomaly` document (and a `AiDetectorHealth.raised` increment) was created for the identical instance on **every single sweep**, up to ~24 duplicate rows for one real anomaly, silently inflating the anomaly count and corrupting the `raised` denominator that A.5's precision math depends on. Reproduced directly before the fix (two sequential `runWorkflow()` calls on an unchanged fixture produced 2 `AiAnomaly` rows for the same detector+entry). **Root-cause fix**: made the key fully deterministic — `idempotencyKey: \`ai-15-anomaly:${a.detectorId}:${a.suppressionKey}:${a.subjectRefs[0]?.id ?? "none"}\`` (no run-specific or time-specific component; combines the detector's own `suppressionKey` with the specific `subjectRef` so two *different* instances that happen to share a coarser suppression key — e.g. two distinct postings to the same rare account — still each get their own row, verified by a dedicated regression test). **Regression tests** (`tests/ai/aiRuntime/ai15AnomalyDetectionEdgeCases.test.ts`): "C.3 duplicate event...", "C.3 concurrent runs...", "C.3 same duplicate-event fix holds for..." (amount_outlier), "C.3 two DIFFERENT instances...each still get their own row" (proves the fix doesn't over-collapse). All four pass; the existing golden dataset and unit suite (12+11 tests) remain green, confirming no regression. **Class check**: grepped every other workflow's `idempotencyKey` construction (`grep -rn "idempotencyKey" lib/aiRuntime/workflows/*/index.ts`) — **AI-15 was the only one of the 30 with a time-based component in its idempotency key**; every other workflow (AI-01, AI-02, AI-03, AI-05, AI-06, AI-07, AI-08, AI-09, AI-10) builds its key purely from stable record/period identifiers (e.g. `ai-01:${extractedDocumentId}`, `ai-07-accrual:${poId}:${lineIndex}`). AI-06's `ai-06-payment-run:${tenantId}:${date-string}` includes a *date*, but deliberately as a once-per-calendar-day dedup key, not a defeat of idempotency — a different, intentional pattern, not the same class. **This is an incident, not a class** — confirmed, not just asserted, by reading every occurrence.
2. **Cross-tenant defect class checked, not found.** Per the brief's specific instruction, checked every DB read in `extract()`, including the three upstream `AiDecisionTrace` lookups — all correctly scoped to `ctx.tenantId`, never to an externally-supplied id (see the dedicated section above). AI-15 has no externally-supplied record id to resolve at all (`ai.sweep.hourly`'s payload is `{}` in production), so the AI-01/02/03/04/07/08/09/10 unscoped-`findById` defect shape structurally cannot occur here. No fix needed; documented with the reasoning, as instructed for a genuine negative result.
