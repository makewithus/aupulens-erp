## 5. Failure paths

- **Missing config (no accounts)**: degrades to findings-only, no draft — golden case
  `revenue-leakage-no-accounts`, section 4.
- **Locked period**: `try/catch` around every tool call in `act()`, period stays pending for next
  sweep — module comments at each call site, generic `check_period_lock` mechanism proven in
  `toolRegistry.test.ts`.
- **Kill switch off**: workflow never dispatched (event bus `requiresValidation` gate) — no
  partial run, no partial write.
- **Permission denied**: `gateOverrides.permissionOk` false → `RECOMMEND`, `act()`'s
  `decision.autonomyApplied !== DRAFT` guard returns immediately with no actions taken.
- **Tool failure mid-pipeline**: per-item `try/catch` in `act()`; `safety.test.ts`'s generic
  mid-pipeline-failure test proves the executor always finalizes an audited trace even when a
  workflow stage throws unrecovered.
- **Malformed source data**: proven not to crash in section 4 (null/missing fields test); never
  guesses an amount, never partially writes (guarded by `o.contracted > 0`, account-existence
  checks).

Every path escalates or no-actions cleanly; none silently swallow an error into a false "clean"
result, and none partially write (every write is a single atomic tool call, each individually
idempotency-keyed).

## 9. Bugs found and fixed

1. **Cross-tenant schedule read in `extract()`'s `schedule.due` branch** —
   `lib/aiRuntime/workflows/ai-09-revenue-recognition/index.ts` (was: `AiSchedule.findById(observed.raw.scheduleId).lean()`
   then `owned = scheduleType === DEFERRED_REVENUE && sourceRef.model === "SaleOrder"`, with **no
   tenant check**). The real event-bus path is protected by `scheduleBelongsTo()`'s dispatch-time
   filter (`lib/aiRuntime/schedules/ownership.ts`), but `ownership.ts`'s own doc comment claims
   "each workflow's `extract()` still re-checks ownership... defense in depth" — that claim was
   false for the tenant dimension specifically. A direct or replayed invocation carrying a real
   `scheduleId` belonging to a *different* tenant would have been read and could have drafted a
   journal referencing that victim tenant's account IDs under the attacker's `tenantId`.
   **Root-cause fix**: added `schedule.tenantId === ctx.tenantId` to the `owned` boolean (one
   line). **Regression test**: `ai09WorkflowEdgeCases.test.ts` ›
   `"cross-tenant hostile: a schedule.due event carrying another tenant's real scheduleId is
   refused..."` — asserts zero journals drafted, victim schedule untouched. Existing tests
   (`ai09RevenueRecognition.test.ts`, golden dataset) re-run clean after the fix.
   **Same class checked across other workflows**: at the time this was found, also confirmed
   present (unfixed) in **AI-07** and **AI-08** — both were fixed by a parallel workstream in this
   same verification pass (`ai-07-accrual-intelligence/index.ts` and `ai-08-prepaid-schedule/
   index.ts` both now scope their `schedule.due`/subject-record reads to `tenantId: ctx.tenantId`
   inline). **AI-10 had the identical shape and was fixed in this same pass** (see AI-10's own
   verification record, section 9). A subsequent full grep sweep across all 30 workflows'
   `index.ts` files (see the Chunk 9 batch-1 consolidation) confirmed no other workflow has this
   defect shape — it was contained to AI-01, AI-02, AI-03, AI-04, AI-07, AI-08, AI-09, AI-10.

2. **Month-length/leap-day boundary in the deferred-revenue schedule's `endDate`** — same defect
   shape as AI-07's `addOneMonthClamped` fix, found by grepping for the same `setUTCMonth`
   mutation pattern across the codebase after that fix landed. `newOverTimeSchedules`' `endDate`
   used plain `endDate.setUTCMonth(endDate.getUTCMonth() + 12)`, which rolls a Feb-29 start date
   into Mar 1/2 of the following (non-leap) year instead of clamping to Feb 28. **Root-cause fix**:
   added a local `addMonthsClamped(date, months)` helper (same logic as AI-07's, generalised to N
   months) and replaced the `setUTCMonth` mutation with it. **Regression test**:
   `ai09WorkflowEdgeCases.test.ts` › `"month-length boundary: a subscription schedule created on
   Feb 29 (leap day) gets an endDate of Feb 28 next year, not Mar 1/2"` — pins system time to
   2028-02-29 (a leap year) and asserts the resulting schedule's `endDate` is 2029-02-28, not
   2029-03-01/02. All existing AI-09 tests and the golden dataset re-run clean after the fix.
